# demucs_custom

Сервис разделения музыки на дорожки: **вокал / барабаны / бас / остальное**.

Мы берём готовую архитектуру [Demucs](https://github.com/facebookresearch/demucs)
(лицензия MIT) и **дообучаем её на своих легальных данных**. Это нужно, чтобы
модель лучше работала с нашим стилем музыки, и чтобы у проекта была чистая
юридическая история: исходный код — MIT, обучающие данные — только свои.

> **Статус проекта:** каркас создан. Все файлы есть, оставшаяся логика помечена
> `# TODO`. Уже работают: `config.py`, `check_demucs.py`, `convert_audio.py`,
> `prepare_data_structure.py`, `data_prep.py`, логирование в `monitor.py`,
> проверки в `deploy.py`. Пошаговый план — в разделе «С чего начать» ниже.

---

## Что умеет Demucs (напоминание)

Обычно Demucs разделяет песню на 4 дорожки:

| Дорожка | Что внутри |
|---------|------------|
| `vocals` | голос, бэкинг-вокал |
| `drums`  | барабаны, перкуссия |
| `bass`   | бас-гитара, низкие частоты |
| `other`  | гитары, клавишные, эффекты, шум |

Базовые веса (`htdemucs`) обучены авторами на большом датасете — они уже
умеют разделять музыку хорошо. Наша задача — **аккуратно подстроить** их под
наши данные, не испортив то, что уже работает.

### Находка 5: предупреждения не должны повторяться

При обучении один трек читается десятки раз (эпохи × батчи). Наивная печать
предупреждения на каждый чих дала бы тысячи одинаковых строк. Поэтому
`CustomDataset` запоминает, про какой трек уже предупредил, и говорит один раз.

### Находка 1 (важная): модель нельзя вызывать напрямую

`get_model("htdemucs")` возвращает **не нейросеть, а обёртку** `BagOfModels`.
Её метод `forward()` специально запрещён:

```
NotImplementedError: Call `apply_model` on this.
```

Правильно — так:

```python
from demucs.apply import apply_model
sources = apply_model(model, wav, device="cpu", shifts=0,
                      split=True, overlap=0.25)
```

`wav` имеет форму `(batch, 2, время)`, результат — `(batch, 4, 2, время)`.

### Находка 2 (важная): порядок дорожек в модели НЕ такой, как в config

Модель выдаёт каналы в порядке `drums, bass, other, vocals`, а в `config.py`
стоит `vocals, drums, bass, other`. Если наивне сохранить каналы по номерам,
вокал сохранится файлом с названием «drums».

Правильно — всегда брать названия у самой модели:

```python
for name, data in zip(model.sources, sources[0]):   # не по своему списку!
    save(name, data)
```

При обучении то же самое: `CustomDataset` отдаёт цели в порядке
`[vocals, drums, bass, other]`, а модель выдаёт `[drums, bass, other, vocals]`.
Готовая функция `reorder_sources_to_model_order()` в `data_prep.py` переставляет
дорожки. **Без неё обучение пойдёт не туда** — модель будет сравнивать свой
вокал с чужими барабанами, и метрики покажут красивую, но бессмысленную цифру.

### Находка 3: сегмент модели — 7.8 сек, а не 10.88 сек

Внутри модель работает кусками по 343 980 семплов (7.8 сек). В `config.py`
стоит 480 000 (10.88 сек). Для дообучения это не поломка, но точность будет
выше, если поменять `segment_length: int = 343980`.

### Находка 4: torchaudio больше не умеет писать wav сам

`torchaudio.save(...)` в версии 2.9+ — это обёртка, которой внутри нужен пакет
`torchcodec`. На этой машине его нет, и вызов падает:

```
ImportError: TorchCodec is required for save_with_torchcodec.
Please install torchcodec to use this function.
```

Поэтому `prepare_data_structure.py` сначала пробует `torchaudio` (как просил
ТЗ), а если не вышло — пишет wav стандартной библиотекой Python (модуль
`wave`). Результат одинаковый: обычный 16-битный PCM WAV, только без лишних
зависимостей. В логе всегда видно, каким способом записаны файлы.

### Оценка времени на CPU

Примерно 1 секунда аудио = 1 секунда расчётов. Значит:

| Длина песни | Время на CPU |
|-------------|--------------|
| 30 секунд | ~30 секунд |
| 3 минуты | ~3 минуты |
| 5 минут | ~5 минут |

С видеокартой CUDA будет в 5-15 раз быстрее.

## Как принести свою музыку (`convert_audio.py`)

Если музыка лежит в mp3, flac или ogg, сначала переведи её в WAV — этого
ждёт и обучение, и разделение на дорожки.

```powershell
python convert_audio.py C:\Users\User\Music output
```

Что получится:

```
output/
├── трек1.wav        ← 44100 Гц, стерео, 16 бит
├── трек2.wav
└── ...
```

Что умеет скрипт:

| Возможность | Как это выглядит |
|-------------|------------------|
| Любые форматы | mp3, flac, ogg, wav и другие (в том числе m4a, aac, opus, wma) |
| Частота | любая приводится к 44100 Гц (проверено: 22050 → 44100, высота тона не меняется) |
| Каналы | моно превращается в стерео, лишние каналы отбрасываются |
| Битность | 16 бит по умолчанию, `--bit-depth 32` для float WAV без потерь |
| Вложенные папки | по умолчанию берёт только верхний уровень, `--recursive` — всё дерево |
| Битые файлы | пропускает и пишет причину, остальные конвертирует |
| Уже готовый WAV | не трогает, если он уже 44100 Гц стерео 16 бит |
| Папки | создаёт выходную папку, если её нет |

Ключевые флаги:

```powershell
# вложенные папки тоже обойти
python convert_audio.py C:\Music output --recursive

# перезаписать всё заново
python convert_audio.py C:\Music output --force

# 32-битный float WAV (нужен пакет soundfile)
python convert_audio.py C:\Music output --bit-depth 32

# другая частота и полная подробность
python convert_audio.py C:\Music output --sample-rate 48000 --verbose
```

Про «столкновение имён». Если в папке есть и `трек.mp3`, и `трек.flac`,
оба хотят стать `трек.wav`. Скрипт **не перетирает** один другим молча:
он оставит первый и скажет про второй, какой файл переименовать. Если
тебе всё равно, какой останется, добавь `--force`.

Проверить, что конвертер честно работает:

```powershell
python _test_convert_audio.py
```

34 проверки: правильная частота и каналы, сохранение высоты тона после
ресемплинга, формат 32-битного файла, пропуск битых файлов, создание
папок, `--force`, `--recursive` и то, что `data_prep.py` принимает
результат конвертации.

Полезно знать: `torchaudio` в этой версии требует пакет `torchcodec`,
которого нет, поэтому `torchaudio.load/save` не работает. Конвертер это
учитывает: он читает звук через `soundfile` (а если он недоступен —
через ffmpeg) и пишет WAV стандартной библиотекой. Поэтому ffmpeg
тебе ставить не обязательно.

## Как загружается модель (`model_loader.py`)

Демucs мы не пишем с нуля — берём готовую модель, скачанную из интернета,
и дообучаем под свою музыку. Этот скрипт как раз отвечает за загрузку.

```powershell
python model_loader.py
```

Первый раз модель (~80 МБ) скачается из интернета, дальше брать её
будно из кэша. Скрипт покажет, что именно он сделал:

```
Загружена модель: htdemucs
  Дорожек      : drums, bass, other, vocals
  Параметров   : 41 984 456
Заморожено 35212376 параметров, разморожено 6772080 параметров
  Проверка: сеть реально выдаёт 4 дорожки по 2 канала (прогон на 1 сек)
```

Три вещи, которые он делает:

| Что | Зачем |
|-----|-------|
| `load_demucs_model()` | скачивает и загружает готовые веса |
| `modify_model_for_custom()` | приводит число дорожек к нужному (для 4 дорожек ничего не меняет) |
| `freeze_layers()` | замораживает всё, кроме декодера — учиться будет 6.8 млн параметров из 42, то есть 16% |

Почему замораживаем почти всю сеть. Энкодер и трансформер — это 75%
модели, и они уже хорошо обучены на миллионах часов музыки. Их
переучивание на твоих данных испортит модель, а памяти и времени
съест вчетверо больше. А вот декодер отвечает именно за разделение на
дорожки — его как раз нужно доучить под твою музыку.

### Про смену числа дорожек

По умолчанию у `htdemucs` 4 дорожки, и это ровно наш случай — скрипт
ничего не трогает. Если понадобится другое число, есть одна тонкость,
на которой легко сломаться.

Дорожки делают **два** выходных слоя, а не один:

```
decoder.3.conv_tr   48 -> 16 каналов    (ветка во времени,  ConvTranspose2d)
tdecoder.3.conv_tr  48 ->  8 каналов    (ветка в спектре,   ConvTranspose1d)
```

Число дорожек влияет на оба, причём по-разному, и дальше в сети есть
`reshape`, который делит каналы на число дорожек. Если переделать
только один слой, модель не станет работать хуже — она упадёт с
непонятной ошибкой про несовпадение размеров. Поэтому перестраиваются
обе ветки, каждая по-своему, а в конце модель реально прогоняется на
секунде тишины и проверяется форма выхода.

Хорошие новости: старые веса при этом не выбрасываются. Дорожки, которые
уже были в модели, получают свои pretrained-веса как есть — учить
заново с нуля не нужно. Новые дорожки инициализируются шумом.

Проверить всё это честно:

```powershell
python _test_model_loader.py
```

62 проверки. Самая важная — что после шага обучения изменились
**только** размороженные веса, а замороженные не тронулись ни на бит
(иначе заморозка не работает и модель потихоньку портится).

## Как измерять ошибку (`custom_loss.py`)

Когда модель ошибается, важно понимать *как* именно. В штатном Demucs
потеря одна — L1 во времени, и она не различает вот эти две ошибки:

- вокал сдвинут на 5 мс — для слушателя почти незаметно, а по L1 это
  огромная ошибка;
- верхние частоты выпали совсем — слышно сразу, а по L1 потеря
  сравнима с предыдущим случаем.

Поэтому считаем две части и складываем:

```
потеря = lambda_freq * ошибка_в_спектре + lambda_time * ошибка_во_времени
```

Временная часть отвечает за общее «похоже на оригинал», спектральная
учит тонкую структуру — сдвиги фазы, пропавшие верха, баланс частот.
Одной части всегда не хватает.

```python
from custom_loss import CustomLoss, sdr_loss

criterion = CustomLoss(lambda_freq=0.5, lambda_time=0.5).to(device)

estimate = model(mixture)             # (B, дорожки, каналы, отсчёты)
loss = criterion(estimate, target)
loss.backward()

# метрика качества: чем МЕНЬШЕ, тем чище (это -SDR)
quality = sdr_loss(estimate, target)
```

Проверить:

```powershell
python custom_loss.py
```

### Про выбор весов 0.5 / 0.5

Это стартовая точка, а не готовый ответ. Два слагаемых измеряются
в разных величинах и их масштабы не совпадают. Посмотри, во что
обходятся части по отдельности, и подправь вес, если одно тонет:

```python
loss, parts = criterion(estimate, target, return_parts=True)
print(parts["freq"], parts["time"])
```

### Про знак в метрике

`SDR` (signal-to-distortion ratio) — это децибелы, и **больше = лучше**.
Но оптимизатор умеет только уменьшать, поэтому `sdr_loss` возвращает
`-SDR`, и в нём **меньше = лучше**. Это разные знаки для одной и той же
величины, и легко перепутать.

Считается SDR по проекции: сначала эталон проецируется на предсказание,
и только остаток считается ошибкой. Без этого метрика ругалась бы на
модель, которая выдала дорожку тише в полтора раза, хотя звучит она
ровно так же.

Для ориентира: случайный шум даёт ровно 0 дБ, приличный результат
15–20 дБ.

### Сколько это стоит памяти

Замерено на процессоре при `batch_size=8`, 4 дорожки, 2 канала,
`segment_length=480000`: одна прямая передача этой потери — около
1.5 ГБ RAM и 0.9 сек, обратный проход примерно вдвое дороже, и это
**сверх** того, что ест сама модель.

Не хватает памяти — три рычага по порядку: уменьшить `batch_size`,
увеличить `hop_length`, уменьшить `n_fft`. При `lambda_freq=0`
частотная часть не считается вообще и потеря становится совсем дешёвой.

## Как настраивается обучение (`optimizer_setup.py`)

Скорость обучения подобрана так, чтобы **не испортить** то, чему Demucs
уже научился. Это не украшение: мы дообучаем чужую модель, и плохо
настроенный оптимизатор способен за несколько эпох снести все 35
миллионов замороженных весов, после чего придётся начинать заново.

```powershell
python optimizer_setup.py
```

```
Optimizer настроен. Trainable params: 6772080
```

Что внутри:

| Что | Значение | Зачем |
|-----|----------|-------|
| Оптимизатор | Adam, только для размороженных | замороженные веса не должны получать шаг оптимимизации |
| `learning_rate` | `1e-4` из config | в 10 раз меньше, чем у самого Demucs: у них обучение с нуля, у нас точечная подстройка |
| `weight_decay` | `1e-5` | небольшая регуляризация |
| Планировщик | `ReduceLROnPlateau` | сам решает, когда замедлиться |
| `patience` | 5 эпох без улучшения | столько ждём, прежде чем снизить скорость |
| `factor` | 0.5 | скорость падает вдвое |
| `min_lr` | `1e-6` | страховка: обучение не встанет совсем |

```python
from optimizer_setup import setup_optimizer, setup_scheduler

optimizer = setup_optimizer(model, config)
scheduler = setup_scheduler(optimizer, config)

for epoch in range(config.epochs):
    train_loss = train_one_epoch(model, train_loader, optimizer, device)
    val_loss = validate(model, val_loader, device)
    scheduler.step(val_loss)          # ТОЛЬКО так, см. ниже
```

### Две вещи, на которых спотыкаются

**1. `scheduler.step()` без аргумента не работает.**
`ReduceLROnPlateau` — единственный планировщик, который смотрит на сами
числа. Он умеет только `scheduler.step(val_loss)`, и передавать надо
потерю на **проверочных** данных, а не на обучающих. Обычный
`step()` бросит `TypeError`.

**2. Если забыть `freeze_layers()`, оптимизатор возьмёт все 42 миллиона
параметров** и за несколько эпох испортит модель. Скрипт это
предупреждает, а не молчит:

```
[!] ВНИМАНИЕ: ни один параметр не заморожен - учится вся сеть целиком
```

### Про `weight_decay`

В задании указано `1e-5`, в `config.py` стоит `1e-4` — разница в десять
раз. Сейчас используется **значение из задания (`1e-5`)**, и при запуске
модуль печатает предупреждение о расхождении, чтобы его нельзя было
потерять из виду. Если нужно наоборот — поменяй `WEIGHT_DECAY` в начале
`optimizer_setup.py`.

## Эпоха обучения и проверки (`train_epoch.py`)

Самый горячий модуль: здесь модель считает миллионы раз. Проверен на
реальном `htdemucs`, 26.09.2026.

```python
from train_epoch import train_one_epoch, validate_one_epoch

train_loss = train_one_epoch(model, train_loader, optimizer,
                             criterion, device)
val_loss = validate_one_epoch(model, val_loader, criterion, device)
scheduler.step(val_loss)      # по проверке, НЕ по обучению
```

### Ловушка 1: модель нельзя звать как обычную сеть

```python
pred = model(mixture)     # так написано в учебнике, и так НЕ будет работать
```

`get_model("htdemucs")` возвращает обёртку `BagOfModels`, у которой
`forward()` намеренно заблокирован:

```python
def forward(self, x):
    raise NotImplementedError("Call `apply_model` on this.")
```

Это не поломка. `apply_model()` умеет нарезать длинный файл на куски с
перекрытием и склеивать обратно, но он предназначен для **разделения
готового файла**, а при обучении мы сами считаем потерю и делаем шаг
оптимизатора.

Поэтому в модуле своя функция `forward_sources()`: обходит обёртку и зовёт
сети внутри, складывая результаты с весами — ровно как `apply_model`, но без
нарезки на куски. Для нашего `htdemucs` сеть одна, но код работает и для
мешков из нескольких сетей.

Проверено: усреднение с весами совпадает с ручным расчётом.

| | дорожка 0 | дорожка 1 |
|---|---|---|
| веса сетей | `1.0, 1.0` | `3.0, 1.0` |
| `forward_sources` | 1.5000 | 1.2500 |
| вручную | 1.5000 | 1.2500 |
| без деления (неверно) | 3.0 | 3.0 |

### Ловушка 2: формат батча

Официальный demucs отдаёт одним куском `(B, S+1, C, T)`, где на нулевом
месте смесь, а дальше дорожки. Наш `CustomDataset` отдаёт **словарь** с
ключами `"mixture"` и `"sources"`. Путать эти два формата — источник очень
неприятных ошибок, поэтому `unpack_batch()` принимает словарь и кортеж
`(mixture, sources)`, а на всё остальное отвечает понятной ошибкой, а не
падением через три строки кода.

### Ловушка 3 (проверена, проблемы НЕТ)

`htdemucs` в режиме обучения не подрезает вход до своей длины `segment`.
Атрибут `segment = 39/5` — это **секунды** (7.8 сек = 343 980 отсчётов), но
на выходе получается ровно столько отсчётов, сколько подали на вход:

| вход | выход (train) | выход (eval) |
|---|---|---|
| 480 000 | 480 000 | 480 000 |
| 343 980 | 343 980 | 343 980 |

Поэтому `config.segment_length = 480000` работает без единой правки модели.

### Обрезка градиентов

```python
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
```

Даже при скорости `1e-4` градиент иногда проскакивает на два порядка больше
обычного — достаточно одного неудачного батча, и `optimizer.step()` вносит
изменение в сто раз больше, чем модель выучила за эпоху. Функция обрезает
вектор до заданной длины:

```
всего = sqrt(сумма квадратов всех градиентов)
если всего > max_norm:  все градиенты *= max_norm / всего
```

Замороженные параметры в сумму не входят: у них `grad = None`, и torch их
пропускает. Обрезка не тратит время на 35 миллионов мёртвых весов.

### Мелочи, которые считаются неправильно «по интуиции»

- **Среднее по примерам, а не среднее по средним.** Последний батч обычно
  меньше остальных, и при усреднении средних он повлиял бы на результат
  сильнее, чем должен. Считаем `sum(loss_i * n_i) / sum(n_i)`.
- **`zero_grad(set_to_none=True)` в конце шага.** Результат тот же, но память
  после `step()` освобождается сразу — сотни мегабайт при наших размерах.
- **Битые батчи не убивают обучение.** Если потеря стала `NaN`, батч
  пропускается, веса не трогаются, выводится предупреждение (не больше трёх
  за эпоху, чтобы не забить консоль).


Загружает настоящий `htdemucs`, замораживает энкодеры, гоняет синтетические

## Полный цикл дообучения (`train_custom.py`)

Сборщик: соединяет `data_prep`, `model_loader`, `custom_loss`,


| файл | что это | размер |
|------|---------|--------|
| `models/custom_demucs.pth` | **лучшая модель**, только веса | ~160 МБ |
| `models/custom_demucs_last.pth` | чекпоинт для продолжения | ~212 МБ |

Лучшая модель сохраняется в чистом `state_dict` — её можно положить в
`inference.py`. Проверено: файл открывается через
`load_state_dict(strict=True)` без ошибок, отличается от pretrained в
176 тензорах (ровно `decoder` + `tdecoder`), в энкодерах — 0.

### Что было не так в скелете

Скелет содержал свои `train_one_epoch()`, `validate()` и `build_model()`.
Они удалены:

- его `train_one_epoch()` **не принимал `criterion`** — то есть в нём не
  было потери;
- его `validate()` — тоже;
- `build_model()` дублировал `model_loader.py`.

### Ловушка 1: нельзя перенести модель на CPU, забыв оптимизатор

Поймать `torch.OutOfMemoryError` мало. Если перенести модель на CPU, а
состояние оптимизатора оставить на видеокарте, следующий шаг упадёт с
невнятным `Expected all tensors to be on the same device`. У Adam внутри
`exp_avg` и `exp_avg_sq` — 54 МБ. Поэтому `move_optimizer_state()`
переносит их вместе с моделью.

Проверено на simulated OOM: попытки идут `cuda → cuda → cpu`, и после
отката `optimizer.step()` действительно работает.

### Ловушка 2: один битый трек не должен убивать обучение

Данные читает `tolerant_loader()`: ошибка чтения файла печатается и
пропускается. Если нечитаемых батчей подряд больше 5 — скорее всего, сломан
сам DataLoader, и эпоха останавливается, чтобы не учиться впустую.

Проверено: битые батчи пропускаются, хорошие доходят; `OutOfMemoryError`
при этом **не** проглатывается, а уходит наверх.

### Ловушка 3: ошибка на единицу в чекпоинтах

`saved_epoch` в чекпоинте — это номер эпохи **как его видит человек**
(1, 2, 3...), то есть 1-based. А цикл `for epoch in range(start_index, ...)`
ждёт индекс **с нуля**. «Эпоха 3» — это индекс 2.

Поэтому `start_index = saved_epoch`, а не `saved_epoch + 1`. Со знаком
плюс эпоха 3 не выполнится никогда: `range(3, 3)` пуст, и скрипт
радостно сообщит, что всё уже отучилось. На этой ошибке проверка и
сломалась — хорошо, что не на настоящих данных.

### Ловушка 4: сохранение через временный файл

`torch.save` пишет на месте 160–212 МБ. Если в этот момент вырубить
питание, останется обрывок, из которого Python уже не загрузит модель —
то есть «лучшая модель» испорчена ровно тогда, когда нужнее всего.
`save_atomic()` пишет во временный файл и переименовывает: оригинал
либо целый, либо его нет.

### Ловушка 5: вопрос, на который нет ответа

Если запустить из скрипта или перенаправления, `input()` падает. Ответом
считается «нет»: чекпоинт остаётся на диске, обучение начинается с
нуля. Начать с нуля и затереть чекпоинт было бы хуже всего.

Проверено: `y` / `yes` / `д` продолжают, `n` / пустая строка / нет ввода —
начинают с нуля, файл при этом не тронут. Битый чекпоинт и чекпоинт от
другой архитектуры не роняют обучение, а тоже дают старт с нуля.

### Если данных нет

Скрипт не будет молча учиться на пустом. Он прямо скажет об этом и
запустит **проверку на шуме**: 2 эпохи, синтетические данные, результат
сохраняется отдельно в `custom_demucs_selftest.pth` — настоящий путь

## Про данные

Готовый скрипт создаёт правильную структуру и проверяет её:

```powershell
python prepare_data_structure.py --num-train 3 --num-valid 2
```

Получится так:

```
custom_dataset/
├── train/                      ← на этих треках модель УЧИТСЯ
│   ├── track_001/
│   │   ├── mixture.wav         ← сумма всех дорожек (это подаётся на вход)
│   │   ├── vocals.wav
│   │   ├── drums.wav
│   │   ├── bass.wav
│   │   └── other.wav
│   ├── track_002/
│   └── ...
└── valid/                      ← на этих модель ПРОВЕРЯЕТСЯ, но не учится
    ├── track_004/
    └── ...
```

Правила, которые важно соблюдать:

| Правило | Почему |
|---------|--------|
| `mixture.wav` = сумма четырёх дорожек | иначе модель учится на неверных данных |
| Формат одинаковый: WAV, 44100 Гц, стерео | иначе часть треков не прочитается |
| Одинаковая длина дорожек внутри трека | иначе нельзя сложить смесь |
| train и valid — **разные** треки | иначе метрики будут красивыми, а модель бесполезной |
| Номера сквозные: train = 001…100, valid = 101…120 | сразу видно, к какому набору относится трек |

Полезные ключи:

| Команда | Что делает |
|---------|-----------|
| `python prepare_data_structure.py --dry-run` | показать план, ничего не создавать |
| `python prepare_data_structure.py --clean` | удалить примеры (только те, что создал скрипт) |
| `python prepare_data_structure.py --force` | перезаписать уже созданные примеры |
| `python prepare_data_structure.py --silence` | писать настоящую тишину вместо шума |
| `python prepare_data_structure.py --help` | все ключи |

> **Сколько места.** Один пример-трек — это 5 файлов по 1.83 МБ = 9.2 МБ.
> Полный набор 100 + 20 = **примерно 1.1 ГБ**. Нужно меньше — уменьши
> `--num-train` и `--num-valid`.

> **Безопасность.** Скрипт никогда не удаляет и не перезаписывает реальные
> треки: каждая созданная папка помечается файлом `.demucs_example`, и если
> метки нет — папка считается настоящей и не трогается (даже с `--force`).

**Про лицензии:** клади сюда только то, на что у тебя есть права. Права на
исходный код Demucs (MIT) не дают прав на чужие записи.

## Про чтение данных (`data_prep.py`)

`data_prep.py` читает треки и отдаёт их в том виде, в котором Demucs их понимает:

```python
from data_prep import CustomDataset, get_custom_loaders

ds = CustomDataset(root_dir="custom_dataset", split="train")
ds[0]["mixture"]   # (2, 480000)         - вход для модели
ds[0]["sources"]   # (4, 2, 480000)     - эталон [vocals, drums, bass, other]
len(ds)            # сколько треков

train_loader, valid_loader = get_custom_loaders(config)
```

| Ключ | Что делает |
|------|-----------|
| `python data_prep.py` | проверить, что данные читаются, и напечатать формы |
| `python data_prep.py --loaders` | собрать настоящие загрузчики для обучения |
| `python data_prep.py --split valid` | проверить проверочную выборку |
| `python data_prep.py --make-examples 3` | если данных нет — создать 3 примера и проверить |
| `python _test_data_prep.py` | автотесты чтения (40+ проверок) |

Класс сам делает: читает только `.wav` (остальное пропускает с предупреждением),
моно превращает в стерео, пересчитывает частоту через `torchaudio.transforms.Resample`,
обрезает дорожки разной длины до самой короткой, дополняет нулями короткие треки,
обрезает длинные.

**Почему данные читаются лениво.** В `__init__` мы только ищем папки и читаем
заголовки файлов (это доли секунды), а звук читается в `__getitem__`. Если
загрузить всё сразу, 100 треков по 10 секунд — это ~1 ГБ оперативной памяти,
а 1000 треков — 10 ГБ, и компьютер зависнет.

## Про config.py

`config.py` — единственный файл, где живут настройки. Меняешь число в нём —
оно меняется во всём проекте.

| Параметр | Значение | Что значит |
|----------|----------|-----------|
| `demucs_model` | `"htdemucs"` | базовая модель Demucs |
| `num_sources` | `4` | сколько дорожек на выходе |
| `sample_rate` | `44100` | частота дискретизации, Гц |
| `segment_length` | `480000` | длина кусочка ≈ 10.9 сек |
| `batch_size` | `8` | сколько кусочков за раз |
| `epochs` | `50` | сколько проходов по данным |
| `learning_rate` | `0.0001` | скорость обучения (низкая — мы дообучаем) |
| `num_workers` | `4` | потоков для чтения данных |
| `device` | `"cpu"` | где считать; есть видеокарта — поставь `"cuda"` |
| `pretrained_model_path` | `None` | свои веса; `None` = скачать базовые |
| `custom_data_path` | `"./custom_dataset"` | папка с данными |
| `output_model_path` | `"./models/custom_demucs.pth"` | куда сохранять модель |

**Почему `learning_rate` такой маленький.** Мы не учим с нуля — модель уже
умная и большая. Большая скорость обучения быстро испортила бы хорошие веса.
Маленький шаг + 50 эпох = аккуратная подстройка под наш стиль.

**Почему `epochs` = 50, а не 500.** 50 эпох достаточно, чтобы модель
«подружилась» с нашими данными. Больше — риск переобучения: модель
запомнит тренировочные треки и начнёт ломаться на новых песнях.

Проверить конфигурацию в любой момент:

```powershell
python config.py
```

Файл покажет все параметры, проверит их значения и подскажет, если что-то
настроено неправильно. Ошибок он не вызывает — только предупреждения.

## Частые проблемы

| Что видишь | Что значит | Что делать |
|------------|-----------|-----------|
| `ModuleNotFoundError: No module named 'torch'` | не установлены зависимости | `pip install -r requirements.txt` |
| `python-multipart` в ошибке 422 | нет библиотеки для загрузки файлов | `pip install python-multipart` |
| `No module named 'multiprocessing'` / подвисает на батче | проблема с воркерами на Windows | поставь в `config.py` `num_workers: int = 0` |
| `CUDA out of memory` | не хватает памяти видеокарты | уменьши `batch_size` до 4 или 2 |
| `FileNotFoundError: ...custom_demucs.pth` | модель ещё не обучена | `python train_custom.py` |
| `ffmpeg` не найден | не читается mp3 | установи ffmpeg и добавь в PATH |
| Порт 8000 занят | порт уже используется | смени `api_port` в `config.py` |
